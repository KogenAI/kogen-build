A Build whose independent review ended with a blocking verdict (`candidate/review_blocked`) can be repaired outside the Build and then resumed with the existing `kogen intent resume <id>` (standalone: `kogen-build resume --project <checkout> --id <id>`). No command or flag is added. The resume verifies the repaired tree fresh, returns the original finding to the same reviewer, and commits only what that reviewer approves after the fresh pass. This holds for a checkpoint of the current format (version 4) and of the immediately previous one (version 3, the Elixir Kogen's).

**What the code does now** (observed on this tree, see Feasibility). `resumeLocked` (build/resume.go) compares the checkout's candidate tree (`repo.Tree(b.Start, nil)`) with the checkpoint's `candidate` for every stage. Any external repair therefore refuses the resume with `candidate/resume_refused: Build <id>: candidate contents/modes or unrelated paths changed: app.txt; inspect the checkpoint and checkout, correct drift or obtain fresh approval for a new Build`, for version 4 and version 3 alike. No run, request or change happens. Reopening already works when the tree is unchanged, and also when the checkpoint's `candidate` is the repaired tree. In that case kogen-review's `Independent.Resume` turns stage `review_verify` with the verdict `changes` into `review_retry_verify`. `retry` then runs a fresh verification (`Env.Verify`) of the checkout and sends the same reviewer conversation one user message. That message holds the delivery diff from the seen tree to the verified tree, the original finding and the fresh results. An approval binds the verified tree. Earlier green evidence and earlier approvals are not used (`record.Verdict = "pending"`). The only thing missing is that the resume refuses the repaired candidate before it gets there.

**What the product does after this change.**

1. **A blocked-review checkpoint.** The checkpoint's continuation is one of:
   - stage `review_verify` whose saved review session (`review.DecodeSession(Continuation.Review)`) has the verdict `changes`. This is the terminal blocking verdict, including a repair-limit stop, which is saved the same way.
   - stage `review_retry_verify` (an explicit reopen of that verdict that stopped before its decision).

   Every other stage is unchanged. That includes `review`, `review_verify` with any other verdict, `review_only`, `commit_failed` and the builder stages: there a changed candidate is still refused as drift with today's text.
2. **The external repair is accepted.** For a blocked-review checkpoint of version 4, or of version 3 read through the legacy decoder, a candidate tree that differs from the checkpoint's `candidate` is not refused. The resume continues as for an unchanged one: a new run, then the routing's `Continue`, then kogen-review's reopen above. The fresh pass is of the checkout as it is now, the repaired tree. Its tree is the one the reviewer's approval binds and the one committed. Nothing restores the checkpoint's candidate over the repair. Nothing replays the saved verdict or treats it as the decision. The repair is left in place when the review stays blocked.
3. **Custody drift refuses as today, before any run or request.** These checks keep their order and texts and come before the candidate comparison: checkout identity, run/index paths, HEAD, uncertain boundaries, protected-contract blocker, approval, `baseline changed: <path>` (protected files, `.kogen/project.yaml`, `.kogen/models.yaml`, the Intent), configuration, the exact approved Intent, and `index/staged custody changed`. A repair that touches any of them is refused with that reason. Every other change of the candidate's contents, modes or paths, including new untracked files, is the repair.
4. **Unchanged.**
   - The reopened review's rules belong to kogen-review, which stays pinned at `v0.0.0-20261104090930-ba84b86318eb`. A maintained finding blocks again in a new version 4 checkpoint at `review_verify` with the verdict `changes`. An approval commits the freshly verified tree.
   - An external reviewer's blocked review is still refused by `externalReviewRefusal` with its current text. Its session cannot be continued.
   - A checkpoint version this Kogen cannot read is still refused with `incompatible checkpoint version <v>` plus the standard next step, before any run or request. For example: `candidate/resume_refused: Build <id>: incompatible checkpoint version 2; inspect the checkpoint and checkout, correct drift or obtain fresh approval for a new Build`.
   - The version 3 decoder, the checkpoint format and the state goldens are unchanged.

**Acceptance harness.** `features/steps/k-review-reopen-after-external-repair__harness.js` holds the Go test `TestKReviewReopenAcceptance` as text. The step file overlays it into `./build` as `build/k_review_reopen_acceptance_test.go`; that file must not be added to the repository. It uses these package test helpers, which the Build keeps: `newEnv`, `newLegacy76Env` with `legacy76Options.state`, `legacyPut`, `legacyDigMap`, `latom`, `legacyDecode`, `legacyTexts`, `landScript`, `submit`, `finding`, `reviewRequests`, `requestInput`, `lastUserText`, `sessionOfRun`, `checkpoint`, `writeCheckpoint`, `commitsSince`, `nativeReviewer`, `writeFile` and `stepsFile`. Each mode prints one `KRR <json>` observation. The step compares it semantically with the feature's JSON.

## Decisions
- A version 3 checkpoint of a blocked review resumes under the same rules as version 4 rather than being refused; the request allows either outcome, and resuming is chosen because the version 3 decoder and kogen-review's reopen already read it (source: request)
- A "stale approval" is a reviewer approval recorded in the checkpoint before the repair (the latest review record and an earlier attempt of the session). It never clears the finding and never stands in for the reopened reviewer's decision after the fresh pass (source: request)
- Custody-relevant changes are exactly the ones resume checks before the candidate today (item 3), as in "custody drift refuses as today". Any other change of the candidate is the external repair (source: request)
- The refusal of a version this Kogen cannot read keeps its current text, which names the version, its reason (incompatible) and the next step (source: request)

## Tests
- An externally repaired version 4 blocked review resumes with a fresh pass of the repaired tree before the same reviewer's decision, gets the finding and the repair's diff, and lands the verified repaired tree when approved: new test in build/review_test.go, and acceptance scenario 1 (integration)
- The same for a version 3 checkpoint at `review_verify` with the verdict `changes` and at `review_retry_verify`: new test in build/legacy76_test.go using the `review_retry_verify` fixture (as is, and with its stage set to `review_verify`), and acceptance scenarios 2 and 4 (integration)
- A repair that does not fix the finding keeps the review blocked with the repair in place and a new blocking checkpoint: the new review_test.go test, and acceptance scenarios 3 and 4 (integration)
- A reviewer approval recorded before the repair does not clear the finding or commit: the new review_test.go test, and acceptance scenario 5 (regression)
- A repair that changes a protected file or the staged index at a blocked-review checkpoint is refused as custody drift, before any run or request: new cases in build/review_test.go or build/resume_test.go, and acceptance scenarios 6 and 7 (regression)
- A changed candidate at any other stage is still refused as drift: TestResumeRefusals (`candidate drift`, `unrelated path`), TestAResumeStillRefusesEveryChangeToWhatIsStaged (`the candidate itself (index untouched)`, stage `review`), TestKReviewVerdictStrandSafety (review-only drift), TestResumeOfAFailedCommitIsRefusedAfterAnEditOrAMovedHeadOrAChangedApproval and TestLegacyResumeRefusals (existing)
- An unreadable checkpoint version is refused naming the version: the `version 1`/`version 2`/`version 999` cases of TestResumeRefusals, and acceptance scenario 8 (existing)
- An unchanged blocked review still reopens under the same reviewer: TestABlockedReviewStopsAndAnExplicitResumeReopensItUnderTheSameReviewer, TestAReopenedReviewSeesFreshRedResultsAndStaleApprovalCannotClearIt and TestALegacyRetryCheckpointSendsTheBlockerAndTheFreshResultsToTheSameReviewer (existing)
