K-MODELS-FILE-BUILD (filed by kogen-delivery, 3 Nov 2026; change_type: fix, consumer of an intended interface change). K-MODELS-FILE (kogen-coordinator candidate 2a4c69a6, landing-tree 34bd82a "Move the model lineup to .kogen/models.yaml") moves the model lineup out of `.kogen/project.yaml`. Package `project` then reads the team lineup from `.kogen/models.yaml`, and a per-machine `.kogen/local/models.yaml` replaces it role by role. A `models:` key in `.kogen/project.yaml` is refused with `environment/models_moved: .kogen/project.yaml still has models:; move that lineup to .kogen/models.yaml` (exit 3). `Template()` and `RenderConfig` write no `models:` block. `project.Baseline` lists `.kogen/models.yaml` right after `.kogen/project.yaml`, whether or not the file exists. `Config` gains `ModelSources` tagged `json:"-"`, so the JSON of a Config does not change. kogen-build@cfd80c2 fails against it in the landing consumer check. This Intent is built again from current main (after K-STATE-GOLDENS 5495132 and K-REVIEW-SEAM b47cde7), because the earlier candidate was built before those landed and three state-golden tests failed with it.

After this change kogen-build's whole test suite passes against kogen-coordinator 2a4c69a6, so delivery can land producer and consumer together in one combined check. The suite also still passes with the coordinator the committed go.mod pins (`github.com/KogenAI/kogen-coordinator v0.0.0-20261102193107-c4a49a4fe84f`). go.mod and go.sum do not change. The configured `format`, `compile`, `vet` and `go-test` checks run with that pin.

Behaviour for users stays as K-MODELS-FILE defines it. kogen-build's production code needs no change, and the Build makes none. It loads the configuration only through `project.LoadConfig` (build.go, resume.go, recover.go) and the baseline only through `project.Baseline`. So against the candidate it already reads `.kogen/models.yaml` and protects it as an acceptance file. `sameConfig` compares Config JSON, which `ModelSources` does not change. legacy.go reads the lineup from an Elixir checkpoint's saved configuration, not from a project file. No kogen-build code writes a project's lineup. Only test code, test fixtures and goldens change. They must compile with both coordinators, so they do not use `project.ParseModels`, `project.ModelsPath`, `project.LocalModelsPath`, `project.SourceDefault`, `project.ModelsTemplate` or `Config.ModelSources`, which the pinned coordinator lacks. They write the path as the literal `.kogen/models.yaml`.

## Which layout a test uses
- One test helper (for example `lineupMoved` in a new build/lineup_layout_test.go) decides at run time where the coordinator the tests are compiled against reads the lineup. The lineup is "moved" exactly when `project.ParseConfig("version: 1\nmodels:\n  build: {model: m, effort: low}\n", "f")` returns a `sys` error with Class `environment` and Reason `models_moved`. The pinned coordinator accepts that text. Build tags, go.mod edits and environment switches are not used.
- Pinned layout (c4a49a4): every test, fixture file and recorded expectation behaves as it does today. The lineup stays in `.kogen/project.yaml`'s `models:` block, and every existing golden and pinned hash keeps passing unchanged.
- Moved layout (2a4c69a6): a fixture project's `.kogen/project.yaml` has no `models:` key. A role the test changes is written to `.kogen/models.yaml`, with today's role keys and values and each role at the top level (for example `build:\n  executor: claude-code\n  model: claude-sonnet-5-5\n  effort: high\n`, or the flow form `build: {provider: anthropic, model: claude-sonnet-5-5, effort: high}`). The test stages and commits that file where it commits `.kogen/project.yaml` today, and before the approval is written, because the approval hash covers it. Roles the test does not set keep `project.DefaultModels()`, as the rendered `models:` block gives them today. A fixture that sets no role has no `.kogen/models.yaml`.
