# Add a test-only -update flag for golden files

Slug: k-golden-update-build
Model: not applicable — a test-only switch that makes each golden test either compare its output with its golden (as today) or write that output into it; no stored state or interacting rules
Acceptance:

K-GOLDEN-UPDATE for kogen-build (Studio issue 22c28a45-a727-4ba6-8a19-0e7731a888a3). The build package's tests compare their output with recorded goldens, and right now nothing can regenerate them: past Builds edited them by hand, and goldens conflicting between two green candidates forced 1.5-3 h rebuilds. After this change, one documented Go test flag, `go test ./... -update`, rewrites every golden of this repository from the current code's actual output. Without the flag, every golden test behaves exactly as today.

The goldens and their tests (all in package `build`; the run filter in the acceptance uses exactly these test names):

| Golden | Test that compares (and, with `-update`, writes) it | Current encoding of the file |
| --- | --- | --- |
| `build/testdata/context-golden.json` | `TestOpeningMessageEqualsTheElixirReference` (also read by `TestNativeOpeningInputEqualsTheOpeningMessage`) | compact JSON, sorted keys, no HTML escaping, no final newline |
| `build/testdata/context-external-golden.json` | `TestContextExternalNativeBytes` | JSON indented by two spaces, HTML escaping (`<` as `<`), final newline |
| `build/testdata/k-revod-gate/parts-requests.json` | `TestKRevodGatePartsUnchanged` | `json.MarshalIndent(got, "", "  ")` of the `[]revodGateRequest` plus a newline (the current write path) |
| `build/testdata/reset-golden.json` | `TestTheLocalResetEqualsTheElixirReference` | compact JSON, sorted keys, no HTML escaping, no final newline |
| `build/testdata/review/material-golden.json` | `TestTheMaterialEqualsTheElixirReference` | compact JSON, sorted keys, no HTML escaping, no final newline |
| `build/testdata/reviewretry/approve.wire.json` | `TestKReviewRetryUnchangedValidRequests` ("approve lands") | exactly the `kogenOwnedRequest` string, no final newline |
| `build/testdata/reviewretry/changes.wire.json` | `TestKReviewRetryUnchangedValidRequests` ("changes is a substantive blocker...") | exactly the `kogenOwnedRequest` string, no final newline |
| `build/testdata/named-feedback-compat.json` | `TestNamedFeedbackCompatibility` | JSON indented by one space, HTML escaping, final newline |

Observed in a scratch Go program: decoding each of these goldens except `parts-requests.json` into `any` with `UseNumber` and encoding it again with `encoding/json` in the listed encoding reproduces its committed bytes exactly; `parts-requests.json` is what its existing struct writer produces.

After this change:

1. **One flag, test-only.** A single `flag.Bool("update", false, ...)` is declared once in a `_test.go` file of package `build` and is the only update path of every golden test above. `go test ./... -update` (any other `go test` flags such as `-run`, `-count=1`, `-v` or `-race` may be added) works because `build` is the module's only package. No non-test Go file of the module imports `flag` or contains the literal `"update"`; it is not a command, flag, configuration key or environment variable of the kogen program or of this library.
2. **Without `-update`: exactly as today.** Every golden test reads its golden and makes the same comparisons, with the same normalization and the same failure on any drift, and writes no file. The existing test-only switch `KOGEN_REVOD_GATE_GOLDEN=write` of `TestKRevodGatePartsUnchanged` is removed (superseded by `-update`): with it set and no `-update`, that test compares and fails on drift instead of writing and skipping.
3. **With `-update`: write from the actual output.** Each golden test computes its output exactly as today and writes into its golden the values it compares, in the normalized form it compares them (masked folders, run ids, trees, cache keys and so on, as each test already replaces them). Everything else in the file is kept as it is: the case inputs of `context-golden.json` (name, model line, model, README, setup, fix, checks, acceptance run, baseline) and recorded fields the Go test reads but does not compare or does not read at all (for example `files` of each `context-golden.json` case, `history[].path` and `tree` of `reset-golden.json`, `start` of `material-golden.json`). The file is written in its existing encoding from the table, with numbers kept as written (`UseNumber`), so a golden that already equals the output is rewritten byte for byte unchanged, and a drifted value changes only that value's bytes: the update is a small reviewable Git diff. A file is replaced whole (written to a temporary file in the same folder, then renamed), and a golden shared by parallel subtests is written once, after all of them have finished (for example from a `t.Cleanup` of the parent test), so no parallel reader sees a partial file and no two writers race (also under `-race`).
4. **`-update` run outcome.** With `-update`, when the goldens' drift is the only difference, the run exits 0: a golden test does not report the drift it has just written as a failure (it passes, or skips after writing), and a test or subtest whose expected bytes come from a golden that another test writes (`TestNativeOpeningInputEqualsTheOpeningMessage`, and the external-builder "with context" subtests of `TestContextExternalNativeBytes` that derive their expectation from stored entries) does not fail because it read the golden before it was rewritten. The tests' other assertions (exit codes, commits, events, scenario sanity checks) still apply. A follow-up run without `-update` passes.
5. **Frozen goldens keep their rule.** `-update` rewrites every golden, including the ones recorded before a change and never meant to change without deliberate intent (`context-external-golden.json`, `reviewretry/*.wire.json`, `k-revod-gate/parts-requests.json`, `named-feedback-compat.json`); such an update shows up as a Git diff that is reviewed like any other change. The comment of each golden test (or of its golden's helper) names its golden, says what it holds and, for a frozen golden, that it must not change without deliberate intent; the comments that now say a golden was written only by `testdata/gen/*.exs` from the Elixir implementation or by `KOGEN_REVOD_GATE_GOLDEN=write` also say that `-update` rewrites it from the current Go code's output. The Elixir generator scripts stay as they are.
6. **Documentation.** README.md's Testing section documents `go test ./... -update` (that literal command) and when to use it: only when a change deliberately changes a golden's recorded output, or to regenerate the goldens on a combined tree after a merge or cherry-pick conflict in them; then review the goldens' diff (frozen goldens need deliberate intent) and run the full checks without the flag. It is never a way to make an unexplained failure pass.
7. **Unchanged.** No golden file's bytes change in this Build (each keeps its 3b0b3dd SHA-256 digest from the acceptance), no comparison is weakened, no timeout is raised, no new user-visible option is added, and the fixtures stay synthetic. `testdata/legacy*` checkpoints are Elixir-written inputs, not goldens, and are untouched.

## Decisions
- The flag is spelled `-update` and is run as `go test ./... -update` (source: request)
- The flag is read only by the tests; it is never a CLI command, flag, config key or environment variable of the kogen binary (source: request)
- Without the flag every golden test compares and fails on drift exactly as today; with it the tests write the goldens; a follow-up plain run passes (source: request)
- Frozen goldens are also rewritten by `-update`, and their change is a reviewable diff; each test's comment says what its golden holds (source: request)
- README.md documents the command and when to use it (source: request)

## Tests
- Without `-update` every golden test compares as today, fails on drift and writes nothing, and `KOGEN_REVOD_GATE_GOLDEN=write` no longer writes: scenario 1, first run over goldens drifted in a scratch copy (scenario)
- With `-update` every golden test writes its golden from the current output in its existing encoding, restoring each drifted golden to its exact recorded bytes, and the run exits 0: scenario 1, second run (scenario)
- A follow-up run without `-update` passes: scenario 1, third run (scenario)
- The golden comparisons themselves are unchanged: the existing golden tests pass on the unchanged goldens (existing)
- The switch is test-only and documented in README.md: scenario 2 (scenario)
