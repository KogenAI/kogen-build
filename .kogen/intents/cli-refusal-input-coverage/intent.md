# Name missing modes and malformed binding files

Slug: cli-refusal-input-coverage
Model: not applicable — both cases are immediate argument refusals with no new state or lifecycle rules.
Acceptance:
- .kogen/intents/cli-refusal-input-coverage/acceptance.feature
- features/steps/cli-refusal-input-coverage__steps.js
- features/steps/cli-refusal-input-coverage__observer.js

Improve the standalone `kogen-build` usage refusals reported in `ev-8b3fa175`. Replace the incomplete two-mode diagnostic and identify a binding file whose contents cannot be decoded. Implementation changes are limited to `cmd/kogen-build/main.go` and `cmd/kogen-build/main_test.go`. Valid command behavior and continuation binding fields are out of scope.

## Decisions
- When invoked with no mode, return the existing JSON usage refusal (process status and `exit_code` 2, `error.category` `usage` and `error.kind` `invalid_arguments`) and identify `build`, `resume`, and `prepare-continuation` as supported modes in `error.message`. Keep the usage-form guidance consistent with the supported modes, without changing argument parsing. (evidence: cmd/kogen-build/main.go; README.md) (source: request)
- When JSON from `--binding` fails to decode, return the same kind of structured usage refusal and name the supplied file path in `error.message`, retaining the flag and decoder diagnostic. Leave file-read failures unchanged. (evidence: cmd/kogen-build/main.go) (source: request)
- Existing valid `prepare-continuation` arguments still parse, and malformed binding input does not invoke continuation preparation. Return from the decode refusal before calling `PrepareContinuation`; the JSON usage refusal has no `continuation` evidence. Do not change decoding rules, the binding data, or native holds after successful decoding. (evidence: cmd/kogen-build/main.go; cmd/kogen-build/main_test.go; build/continuation.go) (source: request)

## Source comparison
- Addressed: `ev-8b3fa175` and acceptance 1 name the missing documented mode; the first Decision and the no-mode scenario require all three documented mode names in the normal JSON refusal.
- Superseded: `cmd/kogen-build/main.go` currently reports only `build` and `resume` in its no-mode refusal and shared usage forms. The first Decision replaces the incomplete guidance; the invocation syntax documented in `README.md` remains authoritative.
- Addressed: acceptance 2 and its flag-only/decoder-only counterexample are covered by the second Decision and the malformed-binding scenario, which checks for the supplied path rather than just the flag or basename.
- Addressed: acceptance 3 and its parsing/fallthrough counterexamples are covered by the third Decision, the existing parser test, and the paired native hold and usage refusal in the same CLI scenario. The README's continuation evidence on refusal is preserved for native holds; a pre-preparation argument refusal still has no plan.
- Omitted by scope: changes to valid `build`, `resume` or `prepare-continuation` behavior, the continuation binding fields, read failures, documentation, and the continuation adapter are not implementation work for this Intent. No source conflict or scope expansion is proposed.

## Tests
- No-mode refusal reports all supported modes in the normal JSON envelope: add a standalone CLI regression case in `cmd/kogen-build/main_test.go`; the no-mode acceptance scenario also exercises the compiled entry point (regression)
- Malformed binding reports the supplied path and returns before continuation preparation: add a standalone CLI regression case in `cmd/kogen-build/main_test.go`; the malformed-binding scenario contrasts the argument refusal without evidence with the native hold that would accompany preparation (regression)
- Valid preparation arguments still parse: keep `TestParsePrepareContinuation` and verify the supplied project along with mode, ID, and binding path; acceptance also sends a decodable binding through the unchanged native hold on a scratch non-repository project (existing)
