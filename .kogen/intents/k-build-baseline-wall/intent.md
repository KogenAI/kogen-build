# Record baseline wall time and name baseline stops

Slug: k-build-baseline-wall
Model: not applicable — the change adds timestamps to existing run records and one marker to the stop record of a single linear startup step; there are no interacting states or transitions to model
Acceptance:
- .kogen/intents/k-build-baseline-wall/acceptance.feature
- features/steps/k_build_baseline_wall_steps.js
- features/steps/k_build_baseline_wall_test.go.txt

The check baseline (every configured check run once on the unchanged tree before the Build edits anything, `recordBaseline` in `build/baseline.go`) can take most of a cell's wall time. Today its duration is not recorded anywhere a reader looks, and a Build that ends while the baseline runs reports a stop that looks like any other stop. After this change, the baseline's run-log records carry each check's start and end instants and its wall time. They also carry the start, end and wall time of the whole baseline. When a Build ends while a baseline check runs, its stop record (the `outcome` event, `result.json` and the stop report on stdout) names the baseline and that check.

Boundaries: there is no change to bounds, deadlines, timeouts, the no-progress watch, exit codes or the `outcome` value. There is no change to what the baseline decides: which checks run, their order, statuses and outputs, `baseline_checks.checks` and `.failing`, the `baseline:` stdout lines, the builder and reviewer baseline text, and `check_comparison`. The persisted checkpoint state is unchanged: there are no new `State` fields, `check_baseline` keeps the `verify.CommandResult` shape, and the state goldens do not change. Nothing is removed. The change lives in kogen-build's `build/baseline.go`, plus the stop report in `build/stop.go` and the tests. It does not touch `build/core`, `durable/`, detect.go or the Intent validators. Whatever the external cell harness does with these records is outside this repository.

Acceptance harness: `features/steps/k_build_baseline_wall_test.go.txt` is a standalone Go `main` program, not a Go test, despite its file name. The step file overlays it as `internal/kbwdriver/main.go` (`go build -overlay`) and runs it once per mode. The program creates a temporary Git fixture with an approved Intent, a signed-in home and a local provider that refuses every request. It runs real Builds through the exported `build.Build(ctx, *sys.Session, build.Input)` entry point and judges `log.jsonl`, `result.json` and stdout. Modes `wall`, `stop` and `setup` are the acceptance cases. Modes `good` and `bad` are the observer controls on synthetic records.

## Decisions
- Instants use the run log's existing format, `core.ISOTime` (UTC, `2006-01-02T15:04:05.000000Z`, for example `2026-11-03T06:00:00.000000Z`). Wall times are integer milliseconds named `wall_ms`, computed from the same two `time.Time` values as the instants (monotonic difference, `.Milliseconds()`). Format settled during shaping. (source: request)
- Per-check timing: each `command_result` event that `recordBaseline` logs for a check it ran gains `started_at` (taken immediately before the check's command starts, after its `command` event), `ended_at` (taken when its result returns) and `wall_ms` (= ended − started). All existing keys of that event stay unchanged. Verification-pass `command_result` events are unchanged. (source: request)
- Whole-baseline timing: the `baseline_checks` event gains `started_at` (taken when `recordBaseline` begins, before the first check), `ended_at` (taken after the last check), `wall_ms`, and `timings`. `timings` is an array in configured order with one object per check the baseline ran, with exactly the keys `name`, `started_at`, `ended_at` and `wall_ms`, holding the same values as that check's `command_result`. A `:` check whose evidence was reused (`baseline_reuse` event) did not run: it gets no `command_result` and no `timings` entry, but it still lies within the baseline's span. `checks` and `failing` are unchanged. (source: request)
- A baseline check is "in progress" from just before its `command` event until its result returns. This decision covers a Build that ends while a baseline check is in progress, either by a caller interrupt (`*sys.Interrupted`, reported by `interrupted`) or by an error stop (`*sys.Error`, reported by `stopped`, for example `environment/command_no_progress` from the watched baseline command). For such a Build, the `outcome` event and `result.json` both gain `"stopped_during": "baseline"` and `"baseline_check": {"name", "command", "started_at", "stopped_at", "wall_ms"}`, with identical values in both. `name` and `command` are the check's configured name and run command. `started_at` is that check's start instant. `stopped_at` is taken when the stop is recorded. `wall_ms` = stopped − started. Field names settled during shaping. (source: request)
- The same stop prints exactly one extra stdout line, `  stopped during the check baseline: check <name> (<command>) ran <wall_ms> ms (started <started_at>)`, using the same values as `baseline_check`. It comes after the stop's own lines (for an interrupt, after `candidate/interrupted: Build <id> stopped by <signal>; edits are left in place`; for an error stop, after its rendered error) and before the remaining report lines (still failing, comparison, edited, run log). It is printed whether or not the stop is otherwise reported. Line wording settled during shaping. (source: request)
- The existing lines `stopped <slug>: interrupted (Build <id>)` and `candidate/interrupted: ...`, the `outcome` value (`interrupted` or the error's reason) and the exit code (143 for SIGTERM, 130 for SIGINT) stay exactly as today. (source: request)
- A Build that ends with no baseline check in progress (for example, interrupted during setup, or stopped after the baseline completed) has no `stopped_during` or `baseline_check` key and no such stdout line. In particular, a resumed run never runs the baseline. (source: request)
- The in-progress check is kept on the in-memory `Attempt` (unexported), not in the persisted `State`, so checkpoint bytes and the state goldens stay as they are. Settled during shaping from "no change to what the baseline decides". (source: request)

## Source comparison
- Addressed: "the baseline record carries its own start/end instants and wall time per check". This is the per-check `started_at`/`ended_at`/`wall_ms` on each baseline `command_result`, plus the whole-baseline span and the ordered `timings` on `baseline_checks` (Decisions 1-3; acceptance scenario 1).
- Addressed: "the stop reason of a cell that ends while the baseline runs names the baseline". This is `stopped_during: baseline` with `baseline_check` in the `outcome` event and `result.json`, plus the stdout line (Decisions 4-6; acceptance scenario 2). The counterexample, a stop outside the baseline, carries none of these (Decision 7; scenario 2's setup step and the completed-baseline check in scenario 1).
- Addressed: "No change to bounds or to what the baseline decides". Existing outputs, exit codes, outcome values, deadlines and checkpoint state are unchanged (Boundaries; Decision 8; existing tests and state goldens).
- Retargeted: the request's `project/baseline.go` (kogen-coordinator, c4a49a4) lists only protected paths. The checks run, and `baseline_checks` is logged, in kogen-build's `build/baseline.go`, which is where this change goes. The request's "its test/golden" becomes this repository's baseline tests. No golden records the affected events, so no golden changes.
- Evidence only, not reproduced: Studio baseline `bin/rails test` took 1,392-2,104 s (versus 50-60 s on eu2), and the aorctl-st2rr/aorctl-st2 cells were lost to the 3600 s cell deadline and recorded as a build `timeout`. That deadline and the harness's classification live outside this repository and are unchanged. Acceptance uses short local checks instead (`sleep 1`, and SIGTERM after at least 400 ms).
- Out of scope (request Independence): `durable/` (K-COORD-RUN-STATE-RETAIN), detect.go, the Intent validators.

## Tests
- Each baseline check that runs logs `started_at`, `ended_at` and `wall_ms` on its `command_result`, in order and consistent with each other: acceptance scenario 1 runs the driver in mode `wall`, a real `build.Build` with checks `slow` (`sleep 1; echo SLOW-MARKER`) and `fast` (`echo FAST-MARKER; exit 3`). Also add assertions to `build/failing_check_test.go` (for example `TestFailingCheckBuildEvidence`) that every baseline `command_result` carries the three keys, in the ISOTime format and consistent with each other (integration)
- `baseline_checks` carries `started_at`/`ended_at`/`wall_ms` spanning its checks and a `timings` array equal to the checks' values in configured order, with `checks` and `failing` unchanged: the same scenario, plus the same Go test asserting `timings` names in configured order (integration)
- A reused `:` check has no `timings` entry: add an assertion to the reuse case in `build/baseline_cache_test.go` (for example `TestBaselinePerBaseEligibility` or `TestBaselinePerBaseFailures`) that `baseline_checks.timings` omits the reused check (integration)
- A Build interrupted while a baseline check runs records `stopped_during: baseline` and `baseline_check` identically in the `outcome` event and `result.json`, and prints the stop line, while the existing interrupt lines, outcome `interrupted` and exit 143 stay unchanged: acceptance scenario 2 runs the driver in mode `stop`. Also add a Go test in the build package that interrupts a check that is a running `sleep` (integration)
- An error stop while a baseline check runs carries the same fields and line, with its own outcome reason and exit unchanged: add a Go test in the build package that ends a Build through the error-stop path while a baseline check is in progress, and asserts result.json, the outcome event and stdout (integration)
- A Build that ends with no baseline check in progress names no baseline: scenario 2 runs the driver in mode `setup`, and scenario 1 checks the completed-baseline `result.json`. `TestAnInterruptedStartupRestoresTheIndexAndCannotResume` stays unchanged (existing)
- What the baseline decides, the checkpoint state and the goldens are unchanged: the existing baseline, failing-check, state-golden and full configured checks (format, compile, vet, go-test) pass without `-update` (existing)

## Feasibility
- Scratch runs of the driver program on the unchanged tree (`go build -overlay`, then the binary; a few seconds each). Mode `wall` fails with `command_result slow: started_at = <nil>, want a UTC instant like 2026-11-03T06:00:00.000000Z`, after the check names, order and statuses (slow 0, fast 3) matched. Mode `stop` fails with `result.json outcome=interrupted stopped_during=<nil>, want interrupted baseline`, after the unchanged interrupt lines and exit 143 matched. Mode `setup` passes. That is legitimate missing-feature red, and the fixtures reach the intended behavior through `build.Build`. The step resolves the checkout's real path for both the overlay and `go build`'s working directory, so a symlinked checkout (such as `/tmp` versus `/private/tmp`) builds.
