This fixes findings 1 and 2 of the audit kogenReviewEscapes in package `build`, for both Review routes: the native reviewer (`build/review.go`) and the external reviewer (`build/review_external.go`, which uses the same `reviewRun.evaluate`). Finding 3 (Shape's decision check, `shape/decision.go`) lives in kogen-shaping since the repository split. It is a follow-up item there and is not changed here.

**What the code does now.** The review source is built from the green pass's tree (`materialOf(pass)`). After the reviewer's verdict, the native `loop` and the external `session` read the checkout's current tree with `b.repo.Tree(b.Start, b.Excluded)`. `evaluate` then treats any difference from the pass as a reviewer repair: it verifies that tree and approves it when it is green. A file changed by any other writer while the reviewer works (an editor save, a watcher) is committed as reviewed, although its bytes never reached the reviewer. The audit's scenario and both cases reproduce on this tree: one approval, one commit of "changed outside". Separately, `materialOf` reads `README.md` from the working tree into the authority block "# Project instructions (README.md)", so a builder's README edit becomes reviewer authority.

**What the product does after this change.**

1. **The seen tree.** Every review session keeps the *seen tree*: the tree whose bytes the reviewer holds.
   - It starts as the tree of the pass whose material the session was given. That is `pass.Tree` for a native review. For an external session it is `s.pass.Tree`, both for the review in one session and for each part of a review in parts.
   - **Native only.** Kogen takes the candidate tree (`b.repo.Tree(b.Start, b.Excluded)`) just before and just after each `write_file` and `shell` call it runs for the reviewer. When the tree before the call equals the seen tree, the seen tree becomes the tree after it. Otherwise the seen tree does not change. `read_file`, `view_image`, `list_files`, `search_text` and `submit_review` do not change it.
   - **External.** A round of an external reviewer never advances the seen tree. Kogen cannot tell its edits from any other writer's.
   - Writes by another process during the reviewer's own `write_file` or `shell` call are counted as the reviewer's. Kogen cannot separate them.
   - The seen tree is saved with the review session in the checkpoint, so a resumed native review keeps it. A saved session without one uses its checkpoint pass's tree.
2. **An approval binds only the seen tree.** The tree T is still read after the verdict, as now.
   - A `changes` verdict is handled as now: `review_blocked`, with the edits left in place.
   - An `approve` verdict is applied only when T equals the seen tree. In that case approval works as now. If the pass is green on T, it is approved. Otherwise Kogen verifies, and approves when the verified pass is green and its tree is T. This keeps native reviewer repairs landing in the same single request as today.
   - **Otherwise the approval is not applied and nothing is committed.** This covers two cases: T differs from the seen tree, or the verified tree differs from T. Kogen verifies the current contents (a fresh pass, as now) and returns feedback to the same reviewer. For the native reviewer this is a user message in the same conversation. For the external reviewer it is the next round of the same session, through the existing `lastUserContent` path. Then the seen tree becomes the verified tree, the pass under review becomes that pass, and `repairs` counts one, as the replaced branch did.
   - When the verified tree differs from the seen tree, the feedback begins with this delivery section. `<paths>` are the changed paths between the two trees (`b.repo.Changed`), joined by `, `. `<diff>` is `b.repo.Diff(seen, verified, paths)`, with invalid UTF-8 made U+FFFD. The section ends with one `\n`:
     ```
     Your verdict was not applied: the candidate changed after its contents were delivered to you, other than through your own Kogen tool calls: <paths>.
     The exact diff of these changes against the contents delivered to you:

     <diff>
     ```
   - The paragraph after the section is the existing one for the verification result. When the result is green: `The new tree passed checks but has not been reviewed. Inspect these changes and submit_review for the current contents; do not restart the whole critique.` When it is red: the existing text `Final verification of your repairs failed. …` followed by `PassFeedback`, unchanged. A native reviewer's own failing repair has no delivery section. Its feedback stays exactly as today.
   - With a delivery section, the progress line is `kogen: review <n>: the candidate changed after its contents were delivered; returning the changes to the reviewer`. It replaces `kogen: review <n>: candidate changed after approval; inspecting changed paths`. A red result still prints the existing `kogen: review <n>: final verification failed; continuing targeted repairs` after it.
   - The old feedback `Candidate contents changed after your approval: <paths>. …` is removed. Its case, a change during final verification, now gets the delivery section and the green paragraph.
3. **Explicit resume of a blocked native review (`retry`).** When the freshly verified tree differs from the seen tree, the retry message begins with the delivery section, followed by the existing retry text. Then the seen tree becomes that tree.
4. **Consequence for the external route.** An external reviewer's edit is now confirmed in one more round, where it receives its own diff and must approve again. That round is within the unchanged `max_rounds`, and exceeding the limit stops `candidate/executor_round_limit` as today. External approvals without edits land in one round as today.
   - This loop gets no new limit. It ends at a bound approval, a `changes` verdict, or an existing stop: the external round cap, the invalid-verdict allowances, interruption, or request and usage budgets.
   - The external pre-send custody check (`the candidate changed after its green pass and before the review was sent`) is unchanged. So are the commit stage's baseline, HEAD and tree rechecks.
5. **README is not authority.** In `materialOf`, the "# Project instructions (README.md)" section holds README.md as it was at the Build's start HEAD (`b.repo.Show(b.Start, "README.md")`). When the start HEAD has none, it is `(no README.md)`.
   - The one exception is a `README.md` in the approved baseline (`b.Baseline`). Then the approved bytes in the checkout are used. The existing baseline check keeps them unchanged.
   - A builder's README edit stays in the review source as candidate data, exactly like any other changed file (diff hunks and full text). Both routes take their authority from `materialOf`: the native opening message, and the external `review-<n>-authority.txt` and prompt.
   - The builder's own brief (`build/builder.go`) is unchanged.

Unchanged: the CLI. No limit, timeout or retry is raised. Honest native reviews, with or without `write_file` or `shell` repairs, land as today.

## Decisions
- An approval commits only contents whose bytes reached the reviewer. A later change is returned to the same reviewer as a diff, and needs a fresh explicit verdict (the request allows "a fresh review or is refused at commit") (source: request)
- A builder's edit to README text cannot change reviewer instructions: the project instructions are the README of the Build's start (source: request)
- Honest builds review and land as today. No CLI change, and no limit, timeout or retry is raised (source: request)
- Shape's decision-check coverage (finding 3) is a follow-up item in kogen-shaping, per the repository split (source: request)
