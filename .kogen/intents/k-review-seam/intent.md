# Split review into build/review over build/core

K-REVIEW-SEAM for kogen-build (filed by kogen-delivery on main's order, 3 Nov 2026; owner: finish the kogen-review split; change_type: refactor, behaviour-preserving; depends on K-STATE-GOLDENS, landed in kogen-build 5495132). Today `build` and the independent review share state through one package, so the review cannot move to its own repository (planned: a private KogenAI/kogen-review, moved mechanically after this lands; `build/core` is planned to move into kogen-executor as the shared execution and session contracts). This change splits the module's `build` package into three packages of the same module:

- `github.com/KogenAI/kogen-build/build/core` (package `core`): only what review and build both need — the Attempt/state types and the services they share. It imports no package of this module outside `build/core`.
- `github.com/KogenAI/kogen-build/build/review` (package `review`): the review implementation itself — Review, Resume, the review loop, verdict evaluation and the review tool conversation, of both reviewers (native and external executor). It imports `build/core` and no other package of this module.
- `github.com/KogenAI/kogen-build/build` (package `build`): everything else, keeping its whole current exported API, and running every review by delegating to `build/review`.

Nothing a user, a checkpoint, a run record or a caller observes changes: no behaviour, persisted format, output, CLI, command, flag, setting, environment variable or timeout change, no new dependency (`go.mod`, `go.sum` unchanged). What is replaced: the review code in `build` (`build/review.go`, `build/review_external.go`, `build/review_parts.go` and the review conversation parts of `build/review_retry.go`) moves to `build/review`; the shared types and helpers move from `build` to `build/core`, and `build` re-exports them. The earlier attempt (Build 8ef2706e) was blocked at review because `build/review` held only session serialization and a finding-text helper while Review, Resume, the review loop, verdict evaluation and the tool conversation still ran in `build`; this Intent requires the implementation itself to move, and its acceptance tells that apart.

## Rules

1. **Dependency rule.** `go list -deps -test` of `./build/review` names exactly these packages of this module (test variants such as `p [p.test]`, `p.test` and `p_test` count as `p`): `build/core` and `build/review`; of `./build/core` exactly `build/core`. `build/review` and `build/core` are single packages (no subpackages). `build` imports both `build/review` and `build/core`. Packages of other modules (kogen-loop, kogen-coordinator, kogen-executor, kogen-verification, the standard library) are allowed anywhere.
2. **The dependency test.** A new ordinary Go test in a `_test.go` file of `build/review` or `build/core` (no build tag, flag, environment variable or `-short` skip; any name) runs the go command's `go list -deps -test` for `github.com/KogenAI/kogen-build/build/review` and `github.com/KogenAI/kogen-build/build/core` and fails when either names a package of this module outside the allowed set of rule 1; each failure message names the offending package's import path and the package that depends on it (for example `github.com/KogenAI/kogen-build/build/review imports github.com/KogenAI/kogen-build/build/seamprobe, which the dependency rule forbids`). So `go test ./build/core/... ./build/review/...` fails, in that test (not in compiling), when a non-test file of either package imports a new package of this module such as `build/seamprobe`, and passes on the delivered tree.
3. **`build/core` holds** (types keep their field order, field names, field types, JSON tags and custom (un)marshalers, so every encoding stays byte-identical):
   - the persisted Build state and every type it holds that is today declared in `build`: `State`, `Tokens`, `ReviewRecord`, `HistoryRef`, `OwnerContext`, `Continuation`, `Completed`, the `Stage…` constants, `RequestBudget`, `ReviewRetry`, `InvalidReview`, `ExecutorState`, `ExecutorUsage`, `StageProgress`, `StageEvidence` (with its `MarshalJSON`/`UnmarshalJSON`), `StageCustody`, the stage plan entry (today the unexported `stageDef`), the reviewer material set `State` holds through `OwnerContext.InlineMaterial` (today the unexported `materialSet` and the types it holds), and the run record `Run` (with `StartRun`, `Event`, `Log`, `Write`, `PublishCheckpoint`; `State.Run` holds it). Names for today's unexported types are the Build's choice; a field that is not persisted today stays out of the encoding (`json:"-"` when it must be exported).
   - `Approved` and `RequestSpec`, the review contract `core.Reviewer` (`Review(ctx context.Context, b *core.Attempt, pass verify.Pass) (core.Approved, error)` and `Resume(ctx context.Context, b *core.Attempt) (core.Approved, error)`, with the meaning `build.Reviewer` documents today), and `core.Attempt`: a Build in progress as a reviewer sees it — the Build's own `*core.State` (the very value `build.Attempt` embeds, not a copy, so a reviewer's changes to `Review`, `LastReview`, `Repairs`, `Continuation`, `WorkingContext`, `ReviewRetry`… are the Build's) and the services `build` provides, declared as an interface in `build/core`: at least `Save`, `Track`, `Verify`, `BaselineIntact`, `PassFeedback` and `Request` with today's semantics, and whatever else the moved code needs (progress output, the Git tree, diff and file queries of the checkout, the reviewer's native tools, the review material operations, the local facts update, the diagnostic and baseline messages, working-context validation, tool-record fields, the hand-off of a review that ended without a valid verdict…). The interface's name and method set are the Build's choice.
   - helpers both packages use (for example the JSON encoding without HTML escaping that checkpoints use, `nonNil`, zero tokens, token sums), as exported core functions or methods.
   - nothing only one side needs: the checkpoint envelope (`Checkpoint`, `Loaded`) and its decoding and validation, stage-plan validation, verification, the builders, commit, recovery, the legacy importer and the building of the review material stay in `build` (reached by review through the services). A method of a moved type that only `build` uses becomes a `build` function (Go defines methods only in the type's package).
4. **`build/review` holds** the review implementation: the native independent reviewer (today `reviewIndependent` with `reviewRun`: Review, Resume, `save`, `loop`, `retry`, `evaluate`, `converse`, `validate`, `allowance`, `invalidStop`, `seenTree`, `deliverySection`, `nativeResumeBase`, the reviewer tool names and definitions, `reviewNoDefect`, `reviewUnquoted`, `reviewInteger`, `unreadProblemCount`), exported as `review.Independent` (its zero value is the reviewer); the external-executor reviewer (today `reviewExternal` with all of `review_external.go` and `review_parts.go`), exported as `review.External`, which `build` constructs from the executor, its descriptor and the maximum rounds (a constructor or exported fields: the Build's choice); and the reviewer's own saved session (today `reviewSession`, `reviewAttempt`, `reviewVerdict`, `encode`, `reviewDecode`: `Continuation.Review` is the state "which only the review code interprets"), exported for `build`'s legacy importer and tests with the same JSON tags. Both reviewers implement `core.Reviewer`. The review record `review-<n>.json`, the reviewer's run-log events, progress lines and stop errors (`candidate/review_blocked`, `candidate/review_invalid`, `candidate/context_budget_exceeded`, `candidate/context_custody_invalid`) are produced by this code, with today's bytes and texts.
5. **`build` keeps its exported API.** Every exported identifier of package `build` at 6abf7db keeps its kind, type, fields, methods and constant values (`features/steps/k_review_seam/consumer.go.txt` references all of them): the moved types are re-exported as aliases (`type State = core.State`, …), the constants as constants, `StartRun` as a function. `build.Attempt` stays `build`'s own struct embedding `State`, with the exported methods `BaselineIntact`, `PassFeedback`, `Request`, `Save`, `Track` and `Verify` unchanged; `build.Reviewer` keeps its two methods on `*build.Attempt`, and `Deps.Reviewer` still accepts a caller's `build.Reviewer`, which is still called with the Build's `*build.Attempt`. New exported identifiers are allowed only where `build/core` or `build/review` need them.
6. **Delegation.** With `Deps.Reviewer` nil (the native review role), the Build's reviewer runs `review.Independent` on a `core.Attempt` over the Build's own state; an external review role runs `review.External` (built where `selectReviewer` builds `reviewExternal` today). `build` keeps reviewer selection, the `approveWithoutReview` stub, the retry and review-only handling of a review that ended without a valid verdict (`reviewWithRetry`, the review-only checkpoint, the automatic fresh review, discarding the reviewer's edits, the explicit review-only and external-review resumes), the review material building, and `Request`, `Verify`, `Save`, `Track` themselves. No non-test Go file of `build` or `build/core` contains the review conversation's texts (the acceptance lists thirteen of them).
7. **Persisted format and goldens.** The seven K-STATE-GOLDENS goldens under `build/testdata/state/` keep their exact bytes and are not regenerated (their SHA-256 digests are in the acceptance); no file under `build/testdata` is modified, deleted or renamed. Their tests (`TestStateGolden…`, `build/state_golden_test.go`) stay in package `build` with their names and pass; they produce the bytes through the moved production code (the `core` state encoding, the reviewer session's own encoder from `build/review`, the real reviewer through `build`'s default), never a hand-written copy. So a JSON tag change of `State` in `build/core` fails the five checkpoint goldens, and a change of the review record's `effort` key and of the reviewer session's `attempts` tag in `build/review` fails both review records and both review checkpoints.
8. **Existing tests.** Every existing top-level test and fuzz target (the 315 names `go test -list '.*' ./build/...` prints at 6abf7db, in `features/steps/k_review_seam/existing-tests.txt`) still exists, with its name, in a package under `./build/...` and keeps its assertions: a test may move to the package that now holds its subject and may change only identifiers, package qualifiers and constructors; none is deleted, renamed, skipped or weakened. The full suite (`go build ./... && go vet ./... && go test -race -count=1 ./...`) passes.
9. **`-update` keeps working.** Every new package with test files declares the test-only `-update` flag the way `build/golden_update_test.go` does, so README's `go test ./... -update` still runs (a test binary without the flag fails with `flag provided but not defined: -update`, observed); `go test -count=1 ./build/core/... ./build/review/... -update` exits 0.
10. **README.** README.md's `## Packages` list gains one line per new package, after the `build` line, starting with ``- `build/review`: `` and ``- `build/core`: `` — for example ``- `build/review`: the independent review and repair: the native and the external-executor reviewer (review, resume, the review loop, verdict evaluation and the review tool conversation). It imports `build/core` and nothing else of this module.`` and ``- `build/core`: what `build` and `build/review` share: the persisted Build state, the run record, the review contract and the services the review uses. It imports nothing else of this module.`` Nothing else in README changes.

## Decisions
- Move the state shared by build and review into an exported package `build/core`, with json tags that keep the persisted encoding byte-identical (source: request)
- Move the review implementation itself (Review, Resume, the review loop, verdict evaluation, the review tool conversation) into its own package `build/review` that depends only on `build/core` (source: request)
- `build/core` holds only what review and build both need (the Attempt/state types and the services they share) and imports nothing from kogen-build outside `build/core`; `build/review` imports `build/core` and nothing else from kogen-build; a dependency check (go list -deps, in a test) proves both (source: request)
- `build` keeps its existing exported API by delegating to `build/review`; consumers of the current exported API keep compiling (source: request)
- K-STATE-GOLDENS' goldens stay unchanged, not regenerated, and the full test suite passes (source: request)
- No behaviour, format or CLI change; no new commands or flags; no timeout raised (source: request)
