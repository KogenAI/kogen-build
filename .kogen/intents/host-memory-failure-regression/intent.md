# Cover memory failure classification and host stop

Slug: host-memory-failure-regression
Model: not applicable — only regression tests of an existing, unchanged environment failure rule are added; no state or rule changes
Acceptance:
- .kogen/intents/host-memory-failure-regression/acceptance.feature
- features/steps/host-memory-failure-regression__steps.js
- features/steps/host-memory-failure-regression__control.js

This Intent adds model-free regression tests to `build/env_failure_park_test.go` that pin the memory failure behavior of `build/envfailure.go`: each of the three memory phrases that `envFailureKind` recognises (`cannot allocate memory`, `out of memory`, `Out of memory: Killed process`) classifies as memory; a check that reports different recognised memory phrases in consecutive builder passes stops the Build as a host-or-base failure and reports the second pass's line; and a memory failure that follows a different environment failure kind does not stop the Build. Only `build/env_failure_park_test.go` changes. The environment failure phrases, the stop rules and the user-facing messages stay as they are, and `build/envfailure.go` is not edited.

## Decisions
- Add three new test functions to `build/env_failure_park_test.go`, leaving the existing tests unchanged and reusing its existing helpers (`kindStopEnv`, `kindStopScript`, `kindStopNone`): one checks that every one of the three memory phrases, each in its own line, makes `envFailureKind` return `memory`; one runs a Build whose check prints a different recognised memory phrase in each of two consecutive passes and checks that it stops with the host_or_base_failure error and event, after passes 1 and 2, with exit 3 and quoting the second pass's line; one checks that a memory failure in the second pass does not stop the Build when the first pass failed with a different environment failure kind (the file limit, and separately the timeout). (constraint: only build/env_failure_park_test.go changes; build/envfailure.go, its phrases, the stop rules and the messages stay unchanged) (evidence: build/envfailure.go; build/env_failure_park_test.go) (source: request)
- Acceptance cannot name tests the Build writes, so it runs every `Test` function that `build/env_failure_park_test.go` declares beyond the ten it already declares (listed by name in the acceptance control) against the unchanged `build/envfailure.go` (all must pass, and at least one must exist) and against in-memory copies of `build/envfailure.go` with one defect each, each of which at least one of those new tests must reject: one copy per memory phrase that no longer classifies as memory, a copy comparing full lines instead of kinds, a copy quoting the first pass's line, and a copy stopping on any two consecutive environment failures. (constraint: the copies are used through go test -overlay and no checkout file changes) (evidence: build/envfailure.go; build/env_failure_park_test.go; features/steps/facts-history-cap-regression__control.js) (assumption: the Go toolchain in the acceptance environment supports go test -overlay, which a read-only scratch run of the new tests here did) (source: request)
- The scope scenario always requires `build/envfailure.go` to still contain the code the defective copies replace and, only when git status lists changed files (the builder's checkout), requires the files besides the Intent and its acceptance steps to be exactly `build/env_failure_park_test.go`; in a clean candidate checkout the scope is left to the independent review. (constraint: the original scope, only build/env_failure_park_test.go changes, is unchanged) (evidence: features/steps/facts-history-cap-regression__steps.js) (decision: D3, round 1) (source: request)
- Add three new tests to build/env_failure_park_test.go covering memory phrase classification, the different-memory-phrase host-or-base stop quoting the second line, and memory after another kind not stopping; no production file changes. ## Tests
- Each of the three memory phrases classifies as memory: new unit test in `build/env_failure_park_test.go` calling `envFailureKind`; acceptance runs it against the unchanged and the defective copies of `build/envfailure.go` (regression)
- Different recognised memory phrases in consecutive passes stop the Build quoting the second pass's line: new Build test in `build/env_failure_park_test.go` through the existing `kindStopEnv` fixtures (regression)
- A memory failure after a different environment failure kind does not stop the Build: new Build test in `build/env_failure_park_test.go` (regression)
- The environment failure rules stay unchanged and only the park tests change: acceptance scenario 4 (regression)
- The existing host-or-base tests keep passing unchanged: the existing tests in `build/env_failure_park_test.go` (existing)
