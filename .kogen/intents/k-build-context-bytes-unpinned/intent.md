# Compare context bytes without the lineup file

Slug: k-build-context-bytes-unpinned
Model: not applicable — only one test's comparison of recorded request bytes changes; no product state or transition is added
Acceptance:
- .kogen/intents/k-build-context-bytes-unpinned/acceptance.feature
- features/steps/k-build-context-bytes-unpinned__steps.js

This change fixes `TestContextExternalNativeBytes` (build/context_external_test.go), which kogen-coordinator `4826fb1` "Add opt-in model lineup files" (Kogen-Intent: k-models-file) turned red. From that commit on, `project.Baseline` always lists `.kogen/models.yaml` right after `.kogen/project.yaml` (project/baseline.go, `ModelsPath`). So the protected files the Build quotes in its opening requests gain that entry, and so does the approval hash. Coordinator main (`03d7341`, module version `v0.0.0-20261103214825-03d7341feab7`) has the baseline entry but not the later lineup move. At main, `lineupMoved` (build/lineup_layout_test.go) is false, the golden `build/testdata/context-external-golden.json` is not rewritten, and all 8 subtests fail. For example, `native/native_with_context` fails at build/context_external_test.go:481 with `builder differs at byte 17316 (24051 bytes, want 24029)`. In the output that part reads `... - .kogen/project.yaml\n- .kogen/models.yaml\n\nDependency manifests ...`, where the golden has `... - .kogen/project.yaml\n\nDependency manifests ...`. The external-builder parts fail at :474/:499 with `builder.stable differs at byte 17085` (21 extra bytes). The reviewer parts carry `..., .kogen/project.yaml, .kogen/models.yaml.` (20 extra bytes).

After this change the test asserts only what kogen-build contributes to its opening requests: which parts exist, their order and bytes, where the diagnostic message and brief are placed, and the omitted-context equalities. It does not assert whether `.kogen/models.yaml` is a member of the coordinator's protected-file list. It passes with the coordinator go.mod pins (`github.com/KogenAI/kogen-coordinator v0.0.0-20261103113131-ffca7072fe15`), with `4826fb1` (`v0.0.0-20261103201314-4826fb104954`), with main `03d7341`, and after the later lineup move. For these bytes it has no `lineupMoved` branch.

## The rule
- The test compares the protected-file entry `.kogen/models.yaml` present or absent equally. It puts every text through one function before comparing: each part of each golden entry after loading, each part of each subtest's output, the external builder's derived expectations, and the parts it records under `-update`. The external builder's derived expectations are `plain["builder.stable"]` + the diagnostic message, `plain["builder.dynamic"]` and the native builder's reviewer text. The function removes `.kogen/models.yaml` in exactly these forms, which are the reverse of today's `lineupFileForms` and `trackedLineupFileForms`:
  - the sentence list: `, .kogen/project.yaml, .kogen/models.yaml.` becomes `, .kogen/project.yaml.`;
  - the protected-file list items: `- .kogen/project.yaml\n- .kogen/models.yaml\n` becomes `- .kogen/project.yaml\n`. The same applies where JSON text writes the newline as the two characters `\n` or the three characters `\\n`;
  - the sorted list of the project's tracked files, which names `.kogen/models.yaml` when a moved-layout fixture commits it (the external pairings set a role): `.gitignore\n.kogen/models.yaml\n.kogen/project.yaml\n` becomes `.gitignore\n.kogen/project.yaml\n`, in the same three newline forms.
- The function changes no other byte. With the pinned coordinator the texts contain no `.kogen/models.yaml`, so the comparison is exactly today's. Any other difference still fails through `sameBytes`, at its byte offset in the compared texts. The number of parts per entry is still checked, and all 8 subtests still run.
- The per-layout rewrite of the golden in this test is removed: the `withLineupFile` and `withTrackedLineupFile` calls and their `c.extBuild || c.extReview` condition. `lineupMoved`, `withLineupFile` and `lineupFileForms` stay for the other tests that use them (k_reviewretry_valid_test.go, named_feedback_test.go, legacy tests and others). `withTrackedLineupFile` is deleted if it has no remaining caller. Its forms may be reused by the new function.
- The golden `build/testdata/context-external-golden.json` keeps its bytes (SHA-256 `9b753a918827ef61e9072fea1e8af6ec132aed43b64f3a5a921e104cfe698790`) and names no `.kogen/models.yaml`. `go test ./build -run '^TestContextExternalNativeBytes$' -update` records the parts without the lineup file. Run against any of these coordinators, it therefore writes exactly today's golden instead of baking the coordinator's list into it. The test's doc comment says that membership of `.kogen/models.yaml` in the protected files is not compared.
- go.mod and go.sum do not change. The configured checks keep running with the pinned coordinator.

## Decisions
- TestContextExternalNativeBytes compares the protected-file lines (`- .kogen/project.yaml\n`, `..., .kogen/project.yaml.`, and the tracked-files list that `withTrackedLineupFile` handles) with `.kogen/models.yaml` present or absent equally, in the golden and in the output, instead of rewriting them per detected coordinator layout (source: request)
- The test passes with the coordinator before 4826fb1, at main and after the later lineup move, and has no `lineupMoved` branch for these bytes (source: request)
- The golden is not regenerated with the coordinator's list baked in, and the test no longer fails when only the set of protected files changes (source: request)
- Because the lineup file is compared present or absent equally "in the golden and in the output", what `-update` records also leaves out the lineup file, so a deliberate rewrite of the golden against any of these coordinators keeps today's bytes (source: request)
