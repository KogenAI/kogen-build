The route may create a fresh attempt only after it proves (a) no publication or external side effect occurred, (b) no current native owner, process or custody remains, (c) the original accepted request revision and baseline still match, and (d) the old generation's single-writer custody is revoked and fenced. Otherwise it stays held and names the actual owner and the next action. It preserves and archives every prior receipt, identifier, hash, failed result and the spend, and never deletes, replaces or resets them. It creates a fresh unique attempt and generation bound to the exact original accepted request and baseline. It does not run Shape, Build, checks, Review, landing or deployment: those remain the ordinary pipeline's job and every gate is reported pending for the fresh attempt; no old Build, check or Review result can satisfy a gate. The original queue item and Problem20 stay visible and held. The route marks nothing landed, deployed or accepted, makes no push, creates no duplicate queue item and adds no generic reset or auto-retry. It does not alter the accepted request or its acceptance criteria and does not release Problem20.

## Interface contract

The request leaves new code names to the Build; only the operator surface below is fixed, because acceptance must drive one real entry point. Library names, types and helpers are the Build's choice after reusing the existing native recovery helpers (`build/recover.go`: exclusive private archive writes, durable publication) and the standalone envelope (`cmd/kogen-build/main.go`).

Two new standalone modes of `cmd/kogen-build` (the usage text lists them; flags valid for one mode are refused with exit 2 and the offending input named, as the existing modes do):

- `reconstruct --project <checkout> --evidence <file> --archive <absolute-new-directory> [--stop-after preserved|fenced]`
- `reconstruction --project <checkout> --item <queue-item-id>` (read-only readback; it never creates, fences or archives anything)

Stdout is the existing single JSON envelope extended with a `reconstruction` object (also on a hold). Exit status and `exit_code`: 0 for a created reconstruction, a replay of it, or a readback of a created one; 1 for held, interrupted, or a readback of an item with no recorded reconstruction; 2 for usage. A hold carries a non-null `error`. Human progress goes to stderr. No provider, credential or network access is used.

Evidence file (JSON object). Fixture serialization is local machinery; these are the fields the surface reads:
- `queue_item` {`id`, `version`}, `obligation`, `owner` (name of the party holding the obligation), `request` {`document`, `revision`, `sha256`} (the original accepted request), `current_request` {`revision`, `sha256`} (what the queue holds now), `baseline` {`head`} (the original baseline commit);
- `prior`: `attempts` (ids), `builds` (each `id`, `receipt_sha256` and `candidate_tree` as identity values to preserve verbatim, plus `path` of the retained receipt file, absolute or relative to the evidence file, and `copy_sha256`, the SHA-256 of that file's bytes), `spend` (any JSON value, preserved verbatim);
- `effects` {`publication`, `external`}, each `none` (proved), or `unknown`, or `published`;
- `owners`: the list of live native owners, processes or custody holders (each with a `name`); an empty list proves none, an absent field is uncertain;
- `custody` {`generation`, `revoked`}: the old generation and whether its single-writer custody is revoked;
- `claims` {`landed`, `deployed`, `accepted`, `reused_gates`}: any assertion of landing, deployment, acceptance or of an old Build, check or Review result satisfying a gate for the new attempt; the route refuses any such claim.

Eligibility, checked before anything is written. The route is held, with `reason`, `owner` and `next_action`, when any of these holds: `queue_item.id`, `obligation` or `request` is not the Problem20 identity above (this consumer only: another queue item or obligation is never reconstructed, whatever else the evidence proves); `effects` is absent or either value is not `none`; `owners` is absent or nonempty; `custody` is absent or not revoked; `current_request` differs from `request` in revision or SHA-256; `baseline.head` is not the checkout's current HEAD commit; a prior build's receipt file is absent or its bytes do not hash to `copy_sha256`, or the prior attempts, builds or spend are absent; any `claims` assertion is present; the ordinary native Build lock of the checkout is held by another process; or a different reconstruction is already recorded for the queue item (a duplicate reconciliation). `owner` of a hold is the first live owner's name when one is listed, otherwise the evidence `owner`; `next_action` is a nonempty instruction naming what to prove or correct. A hold writes nothing: no archive, no record, no attempt, no wake, and nothing is retried automatically.

Eligible run, in this order, each phase durable before the next and each safe to find already done on a rerun: (1) preserve: create the new `--archive` directory (refused if it exists and is not this reconstruction's own archive) containing byte-identical copies of every retained receipt file and of the evidence file plus a manifest of the identifiers, hashes, candidate trees, attempts and spend; once this phase completes the archive is complete and never modified; (2) fence: durably record that the old generation is fenced and a new generation is allocated, distinct from the old one and from every prior id and hash; (3) create: durably record exactly one fresh attempt and exactly one wake for it. The durable record lives under the checkout's existing local custody area (`.kogen/local`), is keyed by the queue item id and the digest of the evidence bytes, and is written atomically. `--stop-after` ends the run right after the named phase is durable, as a crash would, with state `interrupted`; it exists only so that interruption is observable.

Rerun rules: a rerun with the same evidence continues from the last durable phase (re-proving every prerequisite that can still change, except the custody revocation this reconstruction itself fenced), never repeats a finished phase, never changes the archive, and after creation reports the already-created attempt and wake unchanged without a new attempt, wake or archive (the `--archive` argument of a replay is ignored). A rerun with different evidence bytes for an item that already has a recorded reconstruction is held as a duplicate reconciliation and changes nothing.

`reconstruction` object, for created, held, interrupted and readback (`absent` readback: only `state`, `attempts`, `wakes`):
- `state`: `created`, `held`, `interrupted` or `absent`; `queue_item` {`id`, `version`, `state`: always `held`}; `obligation`; `request` {`document`, `revision`, `sha256`} (the original); `baseline` {`head`}; `archive` (path, when preserved);
- `prior` {`receipts`: [{`build`, `receipt_sha256`, `candidate_tree`, `path`, `copy_sha256`}] in evidence order, `attempts`: ids in evidence order, `spend`: verbatim};
- `generation` {`old`, `new`} once fenced; `attempts` and `wakes`, arrays that are empty until created: an attempt is {`id`, `generation`, `request_revision`, `request_sha256`, `baseline_head`}, a wake is {`id`, `attempt`};
- `gates` {`admission`, `shape`, `build`, `checks`, `review`}: each `pending` for the fresh attempt;
- `landing`, `deployment`, `acceptance`: three separate strings, each `not_observed`; the route never sets any of them;
- `owner`, `next_action`, and `reason` (for a hold).

The README documents both modes. Existing build, resume, prepare-continuation and recovery behavior is unchanged.
