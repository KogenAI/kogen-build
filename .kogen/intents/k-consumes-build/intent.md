# Add consumes suites for each Kogen dependency

Slug: k-consumes-build
Model: not applicable — the change adds test suites and their README; kogen-build's behaviour and state are unchanged

Kogen's repositories depend on each other through Go modules (kogen vendors kogen-loop). Each repository keeps a `contract/` suite for what it provides, but nothing states what a consumer relies on, so a producer's landing has to build and test every consumer in full (the blanket consumer check), which is slow and misses uses no test exercises. The owner's rule is two-sided contracts: each repository also states, as tests, exactly what it consumes. kogen-build keeps `contract/` (what it provides) unchanged and gains one suite per Kogen dependency, each stating exactly what kogen-build relies on from that producer:

- `consumes/kogen-coordinator/`: what kogen-build relies on from kogen-coordinator (module `github.com/KogenAI/kogen-coordinator`).
- `consumes/kogen-executor/`: from kogen-executor (module `github.com/KogenAI/kogen-executor`).
- `consumes/kogen-loop/`: from kogen-loop (module `kogen-loop`, which go.mod replaces with `github.com/KogenAI/kogen-loop`).
- `consumes/kogen-review/`: from kogen-review (module `github.com/KogenAI/kogen-review`).
- `consumes/kogen-verification/`: from kogen-verification (module `github.com/KogenAI/kogen-verification`).

The suites pass at the versions go.mod pins now and run in the repository's normal test command (`go test ./...`, configured as `GOFLAGS=-trimpath go test ./...`). Nothing else changes: `build/`, `cmd/`, `contract/`, `go.mod` and `go.sum` stay byte for byte as committed at HEAD, no command, flag or option is added (the only `main` package outside `features/` stays `github.com/KogenAI/kogen-build/cmd/kogen-build`), and kogen-build's behaviour is the same. `README.md` may gain one bullet naming `consumes/` in its Packages list; nothing else in it changes.

This attempt replaces the review_blocked earlier attempts. Their reviews found that the suites covered only a fraction of the uses, that `consumes/README.md` did not record the full inventory and mapping (including cmd/kogen-build, aliases, re-exports, and methods and fields reached through returned values), and that a mapped test did not assert the result kogen-build relies on: build emits the non-nil event `tools.ReadEvent` returns for an image read (`build/executor_native.go:176`), but the mapped test asserted only that plain text returns nil, so a regression suppressing every image read event would pass. This Intent fixes the inventory below, makes the mapping mechanically checked, and requires the relied-on results of every invoked function to be asserted.

### What a use is

kogen-build's own code is the non-test Go files of the packages of module `github.com/KogenAI/kogen-build` outside `contract/`, `consumes/` and `features/` (today `build` and `cmd/kogen-build`). A use of a producer is every identifier in that code that resolves (go/types `Uses` or `Selections`) to an exported package-level object of a package of the producer's module, named `pkg.Name`, or to a method or field of one of its named types, named `pkg.Type.Member` by the type that declares the member (a promoted member by its declaring type). `pkg` is the last element of the package's import path. This covers import aliases (a use resolves to the producer's object whatever the local import name), type aliases and re-exports (`build/core_names.go` `type Tokens = core.Tokens` and the like count as uses of `core.Tokens`; a field or method reached through a build alias, a returned value or a struct field counts as the producer type's member). The acceptance observer, the Go program whose source `features/steps/k-consumes-build__observer.js` exports, computes exactly this and prints it with `-list`:

```sh
d=$(mktemp -d) && node -e "process.stdout.write(require('./features/steps/k-consumes-build__observer.js').source)" > "$d/main.go" && printf 'module observer\n\ngo 1.27\n' > "$d/go.mod" && (cd "$d" && GOFLAGS= GOWORK=off go build -o observer .) && "$d/observer" -list . kogen-coordinator=github.com/KogenAI/kogen-coordinator kogen-executor=github.com/KogenAI/kogen-executor kogen-loop=kogen-loop kogen-review=github.com/KogenAI/kogen-review kogen-verification=github.com/KogenAI/kogen-verification
```

### Each suite

- One Go package in `consumes/<producer>/` made only of `_test.go` files (any package name, for example `package consumes`). No non-test Go file, no subpackage needed, no build constraint, no `t.Skip`, no sleep.
- Written only against the producer's exported API. It imports only the standard library, the producer's packages, and packages of the other four Kogen dependency modules only where a producer signature needs their values (for example `core.ProviderRole` takes a `project.Role`, `review.Env.Request` returns a `*provider.Response`, `review.Evidence.Pass` is a `verify.Pass`). It never imports a package of kogen-build (`build`, `cmd/kogen-build`, `contract`) and copies no kogen-build private helper; it imports no other module and adds no go.mod requirement. Like `contract/`, a provider exchange may use only an in-process transport (an `httptest` loopback server or an `http.RoundTripper`), never another address.
- Every use in its list is named by at least one of its tests and asserted so that changing what kogen-build relies on fails the suite:
  - The type or signature of each function, method, type, field and constant is pinned at compile time with its types written out (for example `var _ func(string, []string) (*git.Repo, error) = git.Open`), including generic functions and types at the instantiations kogen-build uses (`core.NonNil[string]`, and `route.Cycle`, `route.Resume` and `route.Steps` at type arguments of the test's own).
  - A producer interface that kogen-build implements (`review.Env` by `build/host.go`, `route.Steps` by `build/route.go`, `executor.Executor` and `executor.Session` by `build/executor_native.go`) has its complete method set pinned with every signature written out, so an added, removed or changed method fails the suite. A method of an interface counts as covered only when a test names it through the interface (a call on an interface value or a method expression), not by implementing it in a fake.
  - Every function and method kogen-build actually invokes has the results and effects its call sites in `build/*.go` and `cmd/kogen-build/main.go` rely on asserted through real calls, on each outcome those call sites distinguish. For example: `tools.ReadEvent` returns, for an image tool result, the non-nil `image_read` event (its `event`, `owner`, `call_id` and `status` and the image's metadata) that build records, and nil for a plain text result; `verify.CommandResult` encodes as JSON with exactly the keys `name`, `command`, `status` and `output`, as the command's stdout `checks` list does; `sys.Fail`/`sys.AsError` give the `Class`, `Reason`, `Detail` and `Exit` that become the stdout `error` object and the exit code, and `sys.Error.Render`'s text; the exact stage strings of `route.StageCommit`, `StageCommitFailed`, `StageLanded`, `StageReview`, `StageReviewOnly`, `StageReviewRetry` and `StageReviewVerify`, which build persists in its checkpoints; the role, ending, reason, resume and usage constants of `executor`; the bytes of `core.EncodeJSON`, `project.EncodeJSON`, `core.HashHex` and `project.Hash`; the JSON keys of `core.ReviewRecord`, `core.ExecutorState`, `core.ExecutorUsage` and `core.Tokens` as build writes them, and `core.Tokens.Line` text; `review.Session.Encode` and `review.DecodeSession` round-tripping; the `git.Repo` methods on a Git repository made in `t.TempDir()`; `project.LoadConfig`, `LoadIntent`, `ReadApproval` and `ParseGherkin` of files written in `t.TempDir()`; `route.Cycle` and `route.Resume` driving a test `route.Steps` through the step order build relies on; `loop.Run` and `provider.Client.Respond` against an in-process scripted provider; `review.Independent` and `review.NewExternal` reviewing through a test `review.Env` and a test executor; `verify.Verify` and `verify.Pass` results of a project made in `t.TempDir()`.
  - A use that cannot run offline, without a model, a signed-in harness or a supervisor process (sending to a real provider, `executor.Executor.Start` of a real external executor, `sys.MaybeSupervise` with the supervisor argument, `provider.RequireLogin` with credentials) is pinned by its signature and by the offline outcome kogen-build's call relies on where the producer documents one (for example `sys.MaybeSupervise` returning when its arguments do not start with the supervisor argument, as kogen-build's are).
  - It asserts nothing kogen-build does not use: other exported identifiers of a producer may appear only to arrange or observe a use, and are not inventory items.
- Each assertion message names the inventory item it checks (for example `t.Errorf("tools.ReadEvent: ...")`).
- The same isolation as `contract/`: every Git command or other subprocess the suites start, and every producer call taking an environment, gets an environment without inherited `GIT_*` and `KOGEN_*` variables, with a `HOME` of the suite's own under a temporary directory, `GIT_CONFIG_GLOBAL=/dev/null`, `GIT_CONFIG_NOSYSTEM=1` and `GIT_TERMINAL_PROMPT=0` (a `TestMain` that clears and sets these for the process is the simplest way). No network (only the in-process transports above), no host paths (every file under `t.TempDir()`; no read of kogen-build's sources, `testdata/`, the module cache, the caller's `KOGEN_NODE`/`KOGEN_QUINT`/`KOGEN_CUCUMBER` tools or another repository's files), no shared mutable state between tests; deterministic under `-race -count=1 -shuffle=on` and `-trimpath`.

### consumes/README.md

One `consumes/README.md`, in the manner of `contract/README.md`, states: what each suite pins (what kogen-build relies on from the producer, at the version go.mod pins), how to run them (`go test -race -count=1 ./consumes/...`), their isolation, and how coverage was checked (the go/types listing above of every use in kogen-build's non-test code, per dependency and package, compared with the identifiers the suites' tests name). Its `## Inventory` section has one `### <suite>` heading per suite, exactly `### kogen-coordinator`, `### kogen-executor`, `### kogen-loop`, `### kogen-review` and `### kogen-verification`, each followed by a table with one row per use of that suite's list: the first cell is the use in backquotes and the other cells name the tests asserting it by their Go test function names, for example ``| `tools.ReadEvent` | TestReadEventImage, TestReadEventText |``. At least one test a row names uses the item in its own function body. The inventory lists every use once, under its suite, and nothing else.

### Acceptance

The observer, run on the checkout, must print `ok`: each suite exists, has no non-test Go file and no forbidden import, its tests name every use, and the inventory equals the lists, each row naming existing tests of its suite with at least one whose body uses the item. `go test -count=1 -trimpath ./consumes/...` must pass with an `ok` line (not `[no tests to run]`) for each of the five consumes packages, and `go list ./...` must list them and `contract`; `go test -race -count=1 -shuffle=on ./consumes/...` must pass the same way with a Git dir, work tree and index that do not exist, a fresh `HOME` whose `.gitconfig` signs every commit and tag with a key that does not exist, HTTP proxies that refuse every connection, `GOPROXY=off` and `GOFLAGS=-mod=readonly -buildvcs=false`. `features/steps/k-consumes-build__fixtures.js` holds known-good observer controls (bare references of every use in one test, asserting nothing), not the implementation: the Build writes real tests and does not copy them.

## Decisions
- One suite per Kogen dependency, `consumes/<producer>/` for kogen-coordinator, kogen-executor, kogen-loop, kogen-review and kogen-verification, next to the kept `contract/`, written only against the producer's exported API with `contract/`'s isolation (source: request)
- The coverage table of every use per dependency, with the tests asserting each, is recorded in `consumes/README.md`, as the request's delivery decision states (source: request)
- Every imported identifier of non-test code is covered, including cmd/kogen-build, import aliases, type aliases, re-exports and members reached through returned values, and each invoked function's relied-on results are asserted, as the request's delivery decision and automatic retry state (source: request)
- The suites are written in the same style as `contract/`; whether each test asserts the behaviour kogen-build relies on, beyond naming the use, needs human evaluation by the reviewer; the acceptance observer checks that every use is named, inventoried and mapped to a test whose body uses it (source: request)
- The suites run in `go test ./...` at the pinned versions; no behaviour change, no new command, flag or option, go.mod and go.sum unchanged (source: request)
